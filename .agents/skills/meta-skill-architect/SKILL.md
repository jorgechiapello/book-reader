# Meta Skill Architect: Extensibility Ecosystem Specifications

## Goal

Ensure that any extensibility artifact generated by the AI agent strictly complies with the closed parsing schema of the IDE, guaranteeing that the underlying system indexes, loads, and routes them correctly without triggering silent YAML errors or structural collapses.

## Instructions

When assigned responsibility for creating a new Workflow or a new Skill (whether instantiated manually by the user or through the `/learn` self-improvement loop), you MUST apply the following architectural specifications:

### Structural Specifications for Workflows (`.agents/workflows/`)

1. **File Extension:** Always `.md`.
2. **YAML Frontmatter (Critical):** Absolutely MANDATORY at the start of the file. Only the `description:` field is permitted. NEVER use nested single quotes inside the description string to avoid YAML parser escape failures. Always use double quotes externally, or avoid quotes entirely if the text allows it.
3. **Internal Document Structure:** The Markdown body must begin with a Level 1 heading (`#`), followed by a `Goal:` declaration and a section demarcated by `## Steps:` that sequentially enumerates the procedural instructions.
4. **Physical Size Restriction:** The final rendered file must NOT exceed 12,000 characters under any circumstance, as the engine will truncate or reject the file.

### Structural Specifications for Skills (`.agents/skills/`)

1. **Base Directory Topology:** Create an individual subfolder for the skill using kebab-case format for the name (example: `.agents/skills/api-security-audit/`).
2. **Mandatory Main File:** Inside the newly created directory, you must create the file `SKILL.md`.
3. **YAML Frontmatter (Critical):** Strictly MANDATORY at the beginning of `SKILL.md`. Must contain EXACTLY two semantic fields:
   - `name:` — descriptive name in kebab-case, no spaces, special characters, or uppercase
   - `description:` — highly detailed and semantic instruction that the progressive router will use to decide when to inject this skill into the active context
4. **Internal SKILL.md Structure:** Must organize its instructional logic using the following Level 2 headings (`##`):
   - `## Goal` — What exactly the skill achieves from a functional perspective
   - `## Instructions` — Step-by-step logic, terminal commands, or rules to follow during execution
   - `## Examples` — (Strongly recommended) Few-Shot patterns of user input and expected output
   - `## Constraints` — Negative rules ("Do not") critical for maintaining safe operations

### Structural Specifications for Rules (`.agents/rules/`)

1. **File Extension:** Always `.md`.
2. **No YAML Frontmatter required** — rules are plain Markdown files.
3. **Content:** Passive, imperative, and concise directives. Use bullet points for individual rules.
4. **Scope:** Only create rules for directives that must apply to ALL future interactions. Do not use rules for situational knowledge.

### Structural Specifications for Knowledge (`.agents/knowledge/`)

1. **File Extension:** Always `.md` located directly in the directories (no subfolders needed unless categorizing heavily).
2. **YAML Frontmatter:** Optional, but if present must only use the `description:` field.
3. **Internal Structure:** Group content by clear structural patterns. Common headers include `## Goal`, `## Principles`, `## Examples` (showing Incorrect vs Correct implementations).
4. **Content Logic:** Focus on the "Why" and "Where" lines are drawn in the architecture, rather than the "How" to execute a script. Focus on Composition over Inheritance, DI boundaries, or naming conventions.

## Constraints

- Under NO circumstance include executable Markdown code blocks (triple backtick) directly inside the YAML metadata block delimiters.
- Do NOT invent, infer, or add additional YAML fields not documented here (such as `author:`, `version:`, `dependencies:`). The closed engine will not recognize them and may fail.
- When writing or updating pre-existing files, ALWAYS use standard file modification tools that preserve the original content unaltered outside the explicit scope of the modification.
- When appending to `AGENTS.md`, ONLY append under the `## Lessons Learned (Knowledge Base)` section. NEVER modify content above that section.
- Prefer creating NEW discrete skill files over modifying existing ones, to isolate the impact of self-improvement into modular safe containers.
